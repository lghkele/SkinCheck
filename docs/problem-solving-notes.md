# 暗夜截图检测：遇到的问题与解决思路

更新日期：2026-10-20。实现基线：SkinScan 0.4.0。

本文总结从初版检测到文字测量、图片过滤和文字候选验证的改进过程，按“现象 → 原因 → 解决思路 → 验证与限制”组织。具体参数见[文字算法](text-algorithm.md)、[图片算法](picture-algorithm.md)；算法来源总表见[总体方案](android-dark-mode-screenshot-detection-plan.md)，版本验收见[实现记录](implementation.md)。

## 1. 白色卡片上的灰字为什么被报出来

**现象。** `white_card` 中出现接近白色的卡片和灰色文字。背景和文字分别产生告警，看起来像把同一个问题重复报告。

**原因。** “暗夜主题颜色错配”和“所有文字的可读性不足”是两个检测目标。RGB(245,245,245) 是接近白色的浅灰，RGB(181,181,181) 是灰色；两者实际对比度约为 1.88:1。全量可读性检测会命中这一组合，但这不能直接证明灰字本身没有跟随暗夜主题切换。

**解决思路，0.2.0 已实现。** 明确区分两种范围：

| 模式 | 检测目标 | 白卡灰字如何处理 |
| --- | --- | --- |
| `theme_mismatch`，默认 | 深色局部背景上的暗笔画、浅色局部背景上的亮笔画，并且对比度低 | 不进入专项文字告警；白卡仍由背景链路独立检测 |
| `all_low_contrast` | 极性正确的全部低对比度组合 | 继续检查，实际对比度不变 |

判断依据必须是文字附近的背景，不能用整页深浅代替。默认深色背景范围为 `Yg <= 0.30`，浅色为 `Yg >= 0.75`，中间范围不属于默认专项。

**验证与限制。** 默认模式下 `white_card` 只保留背景异常；全量模式仍可测得约 1.88:1。专项模式没有覆盖全部可读性问题，日间页面本身也不在本工具当前输入范围内。

## 2. 一整行取色会掩盖局部弱文字

**现象。** 同一行里存在正常的深色字和浅灰弱字。把整行颜色汇总成一种前景、一种背景后，可能漏掉浅灰部分；也可能把正常字符一起框入。

**原因。** 一行可以包含多种前景颜色、多个局部背景。抗锯齿像素也会混入取色。整行代表色不能说明某个具体笔画与其实际背景的关系。

**解决思路，0.2.0 已实现。** 行只负责组织候选，测量在组件内部进行：

1. 用相反梯度边缘配对估计局部笔画宽度，借鉴 SWT 的几何思想。
2. 在宽度内部采样稳定核心，在两侧取邻近背景；两侧背景明显不同则拒绝。
3. 每个配对独立计算 WCAG 对比度，检查组件内有多少可靠配对支持异常。
4. 只把异常组件重新组合成文本段，不把整行无条件扩大为异常。

**验证与限制。** `mixed_foreground` 中正常的 `GOOD` 不被框入，弱字 `weak` 能独立定位。组件可能是偏旁或粘连字符，不等于完整单字；当前流程也不是完整 SWT 检测器。极细字体没有稳定核心时仍可能测量失败。

## 3. 图片没有变暗，却被当作未适配背景

**现象。** 书籍封面、照片中的白色天空和亮色内容触发背景异常。用户指出：图片在暗夜模式下本来就可以保持原亮度。

**原因。** 最终截图把图片与 UI 画在同一平面。单看亮度，封面中的白色区域与未适配白卡可能很相似；只看局部纹理，也可能把图片中的平坦天空当作 UI。

**解决思路，0.3.0 已实现。** 先判断哪里有足够的图片证据，再处理其内部背景告警：

1. 学习页面常见的平坦 UI 底色，由非底色像素提出候选范围。
2. 同时比较排除全部常见底色、只排除较暗底色的提案，兼顾白卡嵌图和封面中的白色天空。
3. 联合检查纹理覆盖、多个网格中的细节分布、主色占比、内外边界和重复布局。
4. 对可信候选的原图 ROI 做 Lab SLICO 超像素分割，生成内部支持掩码，并保留边界带。
5. 仅从背景分析中排除可信内部；不确定区域保留，相关告警可降为复核。

这不是“看起来有纹理就整块忽略”，也不是把图片压暗。SLICO 用于细分已经提出的范围，不能独立证明它是封面，更不是封面语义识别。

**验证与限制。** `cover_page` 定位到 9 个可信图片区域、1 个不确定候选；同一版本仅切换图片过滤开关，背景告警从 6 个降到 1 个。纯色海报、深色封面、弱边界和重叠浮层仍可能定位不完整。

## 4. 去掉图片内部后，可能人为制造细边框

**现象。** 从亮区掩码中挖掉图片内部后，四周保护带可能剩成一圈细亮边。如果继续以这个掩码寻找窄边，就会产生原图中不存在的“边框问题”。图片面积很大时，原始全页亮度比例也可能误导整页判断。

**原因。** 图片过滤改变了候选连通结构；同时，整页统计混合了内容图片与需要检查的 UI。

**解决思路，0.3.0 已实现。**

- 块状背景分析使用排除可信图片内部后的有效区。
- 窄边分析保留原始亮度阈值掩码的连通结构；主要落在可信图片内部的原始候选才过滤，避免用挖空结果判断形状。
- 原图亮度统计继续保存，整页未适配规则改用剩余 UI 的统计和面积分母。
- 剩余 UI 太少时标记背景分析不完整，不能因没有候选就当作通过。

**验证与限制。** 回归同时检查“不制造假细边”和“图片外单像素真实细边仍保留”。图片与真实边框粘连时仍可能难以区分，不能保证完全不漏。

## 5. 图片背景误报减少，为什么文字告警没有减少

**现象。** 0.3.0 的 `cover_page` 背景告警从 6 个降到 1 个，但仍有 10 个疑似低对比度文字和 6 个无法稳定测量的候选。

**原因。** 当时图片掩码只接入背景链路，文字仍扫描全部有效像素。形态学会响应字缝、导航栏圆角和封面纹理；可靠笔画配对失败后，旧整行回退仍可能用不正确的前景／背景组合输出低对比度。

核对结果发现，这 10 个低对比度项全部来自 `line_fallback`，不是可靠笔画配对。部分框位于天空、龙身纹理、导航圆角以及文字内部空隙。即使算出一个较低数值，也不能据此确认候选是真实文字。

**解决思路，0.4.0 已实现。** 从算法入口、测量和失败处理同时改进：

| 环节 | 实际改进 | 要避免的副作用 |
| --- | --- | --- |
| 候选验证 | 联合周围同色比例、同色连通、相反极性包围响应，排除字缝和容器结构 | 不能只凭与外界连通就删除开口字形 |
| 宽度筛选 | 距离变换局部极大值近似中轴，排除宽度过于不规则的组件 | 不是精确骨架；装饰字体可能受影响 |
| 图片上下文 | 图片内要求更多可靠配对、不同采样位置和空间跨度、较稳定的宽度 | 保留全部文字有效像素，稳定标签和数字仍测量 |
| 测量重试 | 原方向不足时，有条件尝试邻近的 ±12°，选择有效配对最多的一次 | 不放宽颜色／背景条件，不合并重复射线凑数量 |
| 失败处理 | 删除整行估色低对比度告警，仅对较强 UI 文字排列保留无法测量项 | 无法测量项不附估算对比度；碎片只进入诊断 |

**验证与限制。** 该页文字低对比度项由 10 降到 0，碎片未知项由 6 降到 0，剩余 1 个背景复核项。单字、数字、图片内部稳定弱标签、图片旁弱文字及仅差 2～3 灰阶的真实弱字均有回归验证。未测碎片记录在 `modules.text.candidateValidation`；没有告警不表示所有字都测量正常，失败的孤立真实文字仍可能漏检。

## 6. 如何避免把过滤做成“所有图片、所有短字都不检查”

**问题。** 直接忽略封面整块区域、取消所有单字检测，或者只降低报告数量，都会让误报减少，但也容易漏掉真实问题。

**解决思路，当前实现遵循。**

- 背景与文字独立判断，白卡消失与否不能决定文字链路是否运行。
- 图片掩码不写入通用 `ignored_regions`，不直接删掉文字采样像素。
- 已可靠测量的单字、数字照常保留，只降低自动确认的置信度。
- 只有无可靠测量的未知分流才要求较强的多组件 UI 排列；不能把这一条件误当成全部文字检测的最低字数。
- 对照验证同时包括应排除的纹理／圆角和必须保留的弱字／白卡／细边，不能只看告警总数。

**限制。** 形状像文字的图案仍可能通过检查，截图本身无法可靠区分每个图标和文字，也无法判断设计是否允许某种弱文字。

## 7. 原始像素、输入格式和资源约束

**遇到的问题。** 用户附件扩展名为 `.png`，实际编码是 TIFF；SLICO 不在原来的基础 OpenCV headless 包中；原分辨率的多张并发分析也比早期资源估计占用更多内存。

**解决思路与实际处理。**

- 不根据扩展名假定编码。该附件保留原文件，按 1080×2376 原尺寸无损解码转存为 PNG 后验证，未缩放。工具的正式输入要求仍为 8 位、不透明、无损 PNG，没有放宽为任意图片格式。
- 改用 `opencv-contrib-python-headless` 提供 CPU SLICO，避免混装多个提供 `cv2` 的包，并检查 wheel 安装及项目目录外调用。
- 先提出图片候选，再对原图 ROI 分割；单张内部两条链路并行，截图并发可调，CLI 限制 OpenCV 内部线程。
- 不沿用未经验证的“几十 MB”承诺。初版特定双并发验证曾记录约 664 MiB 峰值 RSS；这不是当前版资源保证，目标 CI 应重新实测。
- 图片模块故障时记录错误，背景回退为不排除图片，文字继续运行；不把执行失败隐藏成正常通过。

## 9. 算法借鉴与工程改进如何区分

| 方法 | 来源 | 本项目实际采用的部分 |
| --- | --- | --- |
| 数学形态学 | [Haralick 等，1987](https://doi.org/10.1109/TPAMI.1987.4767941) | 开闭运算及 Black-hat／Top-hat 的算子基础，尺度融合为工程规则 |
| SWT | [Epshtein 等，CVPR 2010](https://doi.org/10.1109/CVPR.2010.5540041) | 借鉴相反梯度边缘配对与宽度一致性，不是完整 SWT 复现 |
| 距离变换 | [Borgefors，1986](https://doi.org/10.1016/S0734-189X(86)80047-0) | 调用 OpenCV 近似距离变换，局部极值宽度筛选为工程组合 |
| SLIC／SLICO | [Achanta 等，TPAMI 2012](https://doi.org/10.1109/TPAMI.2012.120)及[作者机构说明](https://www.epfl.ch/labs/ivrl/research/slic-superpixels/) | 调用 OpenCV SLICO 细分候选原图 ROI，不承担图片语义判别 |
| 对比度 | [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/#dfn-contrast-ratio) | 使用线性 sRGB 对比度公式；主题范围门控和项目风险分档为自定义规则 |

底色学习、重复布局、双侧背景一致性、同色字缝判断、±12° 重测、图片内支持门限和失败分流均为项目工程设计；引用论文不意味着这些阈值来自论文，也不代表达到了原论文实验性能。CCL 和具体库 API 等完整来源见[总体方案第 25 节](android-dark-mode-screenshot-detection-plan.md#25-论文标准与实现来源)。

## 10. 仍需继续解决的问题

| 问题 | 当前状态 | 后续思路，尚未完成 |
| --- | --- | --- |
| 深色／纯色／极简封面 | 可能缩框、漏定位或仅进入复核 | 建立真实正负样本，评估候选及边界改进，不能简单放宽纹理门限 |
| 浮层覆盖图片 | 可能包含在图片范围里；截图没有语义层级 | 用带标注的叠加按钮样本验证局部稳定底色与边界证据 |
| 极细字、竖排、装饰字体、粘连组件 | 测量或分组可能失败 | 分场景统计漏检，再评估候选拆分、方向组合或跨尺度稳定性 |
| 测量失败的孤立真实文字 | 可能只有诊断计数，没有问题项 | 增强单组件文字结构证据，不能直接恢复旧整行估色告警 |
| 阈值通用性和生产效果 | 没有人工标注业务集或校准概率 | 固定阈值建立标注基线，分别测区域召回、误报和人工复核量 |

后续每次修改都应明确：它解决哪类输入、依据哪些证据、是否改变检测范围、会新增什么漏检风险，以及用哪些正负样本验证。置信度是工程评分；没有告警、没有可靠测量和确认正常必须保持区别。
